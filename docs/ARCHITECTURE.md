# TouchGrass architecture

> Log off. Pull up. A social app for meeting people in real life, launching in Hyderabad.

## 1. System overview

What runs in production today (lean launch, D-165/D-168). `infra/terraform` keeps a full AWS design for when traffic needs it (§10).

```
Clients: Mobile app (Expo, built and updated by EAS) │ Website: landing, waitlist, share pages, admin (Next.js)
        │ HTTPS + WSS
touchgrass.co.in (Namecheap DNS) ──► Railway custom domains, TLS by Railway
  apex → web · api. → api · rt. → realtime · media. → storage
        │
Railway project (Singapore) — one container per service, private network between them
  ├─ api       NestJS modular monolith, REST /v1        (apps/api/src/main.ts; runs migrations before deploy)
  ├─ realtime  Socket.IO gateway, Redis adapter         (apps/api/src/realtime.ts)
  ├─ worker    BullMQ consumers, outbox relay, cron jobs (apps/api/src/worker.ts)
  ├─ web       Next.js SSR (landing, waitlist, share pages, live-location viewer, admin)
  ├─ Redis     cache, rate limits, idempotency, locks, presence, pub/sub, BullMQ
  └─ storage   RustFS (S3-compatible) on a Railway volume — photos and videos
        │
Supabase (Mumbai): PostgreSQL + PostGIS only, through the session pooler with TLS. Data API off, tables locked down.
External services, each behind an adapter (real + fake):
  Firebase Authentication (phone sign-in) · Expo Push · Google Maps Platform · Google Cloud Vision · Brevo email API
  Switched off for launch: Razorpay (no paid plans), MSG91 (no server SMS), weather, analytics
Observability: Pino JSON logs in Railway · Sentry and OpenTelemetry when their variables are set
```

All three backend processes are built from the same package and share infrastructure modules (`coreImports` in `src/app.module.ts`). None keeps in-process state that would break with more than one replica: sessions, rate limits, idempotency records, locks and presence all live in Redis, and cross-instance Socket.IO fan-out goes through the Redis adapter (proven by `test/realtime.int.test.ts`, which runs two gateway instances).

## 3. Backend module boundaries

Each domain is a NestJS module with its own service, repository, DTOs (from `packages/shared`) and tests. **Modules never query each other's tables.** They call another module's exported service interface, or react to domain events.

`auth`, `users`, `profiles`, `interests`, `invites`, `verification`, `social`, `activity`, `cities`, `venues`, `events`, `rsvp`, `hosting`, `discovery`, `chat`, `polls`, `icebreakers`, `media`, `lore`, `feedback`, `reliability`, `gamification`, `recap`, `crews`, `availability`, `payments`, `referrals`, `safety`, `moderation`, `notifications`, `calendar`, `weather`, `admin`, `analytics`.

Phase 2 adds `social`: `social/graph` (`SocialGraphService`: friendships, blocks, contact hashes, dismissals; no dependency on profiles so both profiles and social use it), `social/reports` (report target registry, severity routing), `social/activity` (event-driven feed), and the application layer `SocialService` (squad lists, contact matching, suggestions). `profiles` gained `PeopleService` (person cards).

Phase 1 adds `auth` (OTP, sessions, refresh rotation), `users`, `profiles` (with the `profileAccess` policy and the `SocialGraphReader`/`ProfileStatsReader` ports), `invites`, `cities`, `interests`, `media` (+ worker `MediaProcessor`), `moderation` (queue intake), `account` (the `/me` application layer: settings, consents, devices, export/deletion registry, age gate) and `admin` (audit log + admin API).

Phase 0 ships the platform modules they all build on: `health`, `platform` (feature flags + app config), `common` (rate limiting, idempotency, errors, validation), `infra/*` and `adapters`.

### Authorisation

Enforced in the service layer with explicit, pure policy functions (e.g. `canViewEvent(viewer, event, graph)`), unit-tested for every visibility, block, age and gender rule. Controllers only authenticate; they never decide access.

## 4. Request pipeline

```
request → Helmet → CORS → JSON body (256 kB cap) → URI versioning (/v1)
        → AuthGuard (Bearer JWT, Redis revocation check; @Public routes skip)
        → ActiveUserGuard (status cache; onboarding users only reach @AllowOnboarding routes)
        → RolesGuard (@Roles; super_admin holds every role)
        → RateLimitGuard (global per-IP 600/min + per-user 300/min + route rules; after auth so per-user limits apply)
        → IdempotencyInterceptor (routes marked @Idempotent)
        → ZodPipe (shared schema) → controller → service (policies) → repository
        → AllExceptionsFilter → { error: { code, message, details } }
```

### Error codes

Stable codes from `packages/shared/src/errors.ts`; never renamed once shipped. Stack traces never leave the server, and internal messages are hidden in production.

| Code                                | HTTP | Meaning                                                                                   |
| ----------------------------------- | ---- | ----------------------------------------------------------------------------------------- |
| `VALIDATION_FAILED`                 | 400  | Body/query/params failed the shared Zod schema; `details` lists `{ path, message, code }` |
| `INVALID_CURSOR`                    | 400  | Pagination cursor tampered with or from another list                                      |
| `IDEMPOTENCY_KEY_REQUIRED`          | 400  | Retryable write called without `Idempotency-Key`                                          |
| `UNAUTHENTICATED` / `TOKEN_EXPIRED` | 401  | Missing/invalid or expired access token                                                   |
| `FORBIDDEN` / `FEATURE_DISABLED`    | 403  | Policy denied / feature flag off                                                          |
| `NOT_FOUND`                         | 404  | Includes resources hidden by blocks or visibility (no existence leaks)                    |
| `CONFLICT`                          | 409  | State changed (capacity, concurrent edit, in-flight duplicate)                            |
| `PAYLOAD_TOO_LARGE`                 | 413  | Body or upload over limit                                                                 |
| `UNSUPPORTED_MEDIA_TYPE`            | 415  | Upload type not allowed                                                                   |
| `IDEMPOTENCY_KEY_REUSED`            | 422  | Same key, different request                                                               |
| `APP_UPDATE_REQUIRED`               | 426  | Client below `MIN_SUPPORTED_APP_VERSION`                                                  |
| `RATE_LIMITED`                      | 429  | `Retry-After` header and `details.retryAfterSeconds`                                      |
| `INTERNAL`                          | 500  | Unexpected; logged and sent to Sentry                                                     |
| `DEPENDENCY_UNAVAILABLE`            | 503  | An upstream provider failed or timed out                                                  |

## 5. Data model conventions

- UUID v7 primary keys (time-ordered for index locality), generated by the app (`uuidv7`) or by SQL `uuid_v7()`.
- `created_at` / `updated_at timestamptz` on every table; `updated_at` maintained by the `set_updated_at()` trigger.
- Money is integer **paise**; time is stored in UTC and displayed in `Asia/Kolkata`; phones are E.164.
- `city_id` on every city-scoped table, so data can be partitioned or sharded by city later.
- Location columns are `geography(Point|Polygon, 4326)` with GIST indexes.
- `messages` and `notifications` are range-partitioned by month (`created_at`); `ensure_monthly_partition(parent, date)` creates partitions ahead of time from a scheduled worker job.
- User-generated content that moderation may need is soft-deleted (`deleted_at`).
- Migrations: `apps/api/migrations/NNNN_name/{up,down}.sql`, checksummed, applied under an advisory lock (DECISIONS D-005).

## 6. Cross-cutting mechanisms

### Transactional outbox

State changes and their domain events are written in **one transaction** (`OutboxService.add(tx, event)`). The worker's `OutboxRelay` claims unpublished rows with `FOR UPDATE SKIP LOCKED`, enqueues them on BullMQ `domain-events` with `jobId = outbox id` (so a crash between enqueue and commit cannot duplicate a job), then marks them published. The `DomainEventBus` dispatches each job to subscribed handlers (badges, notifications, reliability, analytics…). Delivery is at-least-once, so handlers are idempotent.

### Idempotency

`@Idempotent()` routes (RSVP, payments, invites) require `Idempotency-Key`. See DECISIONS D-014.

### Rate limiting

Sliding-window log in Redis via Lua (DECISIONS D-012). Global defaults: 600/min per IP and 300/min per user. Stricter per-route rules come with the endpoints: OTP send (per phone and per IP), invites, friend requests, messages, reports and RSVPs.

### Caching

Hot reads (event detail, feed pages per user per filter, profile cards, flags) are cached in Redis under versioned keys (`cache:<entity>:v1:<id>`) and invalidated explicitly on write. Flags use a 30 s TTL keyed by a generation counter that every write bumps, so a reader that loaded the old rows before a write committed can only fill a key nobody reads any more (D-117). The event cache (`cache:event:v1:<id>`, 5 min) holds the event _core_ only: never the exact location (read separately on the reveal path) and never counts or viewer state (read live), so RSVPs do not invalidate it; edits, publish, cancel, completion and account purges do.

### Locking hot rows

Seat-changing writes (pull up, drop out, waitlist claims, capacity edits, co-host seats) take a short Redis mutex per event (`withRedisLock`, SET NX PX + token-checked release, 2–12 ms jittered polling) **and** `SELECT … FOR UPDATE` on the event row, then count seats inside the transaction. The Redis lock keeps waiting requests off database connections; the row lock is the correctness guarantee. `infra/k6/rsvp.js` load-tests the hot-plan case (CI job `load`): ~40 RSVP writes/s on one plan on a single API instance at p95 < 50 ms, zero errors, never over capacity. Throughput per instance is CPU-bound (Node), so it scales with ECS tasks.

### Discovery feed

`GET /v1/discover/feed` builds a ranked _snapshot_ per request: candidates come from `EventSearchService` (events module; published plans in the time window within the radius of the **public centre**, visibility pre-filtered in SQL), are re-checked with `canViewEvent`, scored by the pure `ranking.ts` (`DISCOVERY_WEIGHTS`, explainable reasons) and stored in Redis for 5 minutes (`feed:v1:snap:<user>:<requestId>`). Pages are slices of that snapshot behind an opaque cursor, so the order cannot shuffle while scrolling; an expired snapshot returns `INVALID_CURSOR` and the client reloads from the top. The same first-page request within 60 s reuses the snapshot. Each served page is hydrated through the mystery-safe serializer (plans the viewer has since joined are dropped) and logged to `discovery_impressions`; clicks go to `discovery_clicks`. Both log tables are monthly range partitions maintained by `PartitionService` (6 / 12 months retention). The map and search reuse the same candidate and visibility path.

### Pagination

Keyset (cursor) pagination everywhere: the cursor is base64url JSON of the last row's sort keys (`TimeIdCursor` = `{t, id}`), validated with Zod on decode. Offsets are never used.

### Media pipeline

Client compresses → API issues a presigned **POST** (size and type enforced by S3) → client uploads directly → `media.uploaded` event → worker downloads, strips EXIF (location), resizes to webp at 160/480/1080 px, runs moderation → `media_assets` state `safe` / `flagged` (held for review). Story videos (D-164) take a second path in the same worker: ffmpeg re-encodes to H.264/AAC MP4 (≤ 720 px short side, ≤ 15 s, no metadata, local-file protocol only), the first frame becomes the webp poster variants, three sampled frames are moderated, and `duration_ms` is stored.

### Payments (Phase 6)

Checkout: `POST /v1/events/:id/checkout` → (event lock) RSVP `held` + `payments` row → Razorpay order → app opens `/pay/<token>` → Razorpay → signed webhook `POST /v1/webhooks/razorpay` → `payment_webhook_events` (once) → `webhooks` queue → worker → (event lock) `held` → `going`, receipt number, outbox `payment.captured` (receipt email). Refunds and payouts follow the same rule: rows are written with the decision, the worker talks to Razorpay, and only webhooks mark money as moved (DECISIONS D-065…D-069).

### After the event (Phase 7)

Feedback, host ratings, reconnect pulls and Lore live in their own modules and reach events only through `EventSearchService` / `EventAccess` and the `EventHooks.lore` hook. Reliability is a ledger (`reliability_events`, one row per person, plan and kind, so replays are no-ops) written by worker handlers on `event.completed` (check-ins and no-shows) and late `rsvp.cancelled`; scores and cooldowns are recomputed from the ledger with the shared `reliabilityOutcome` and read back through the DB-only `ReliabilityReaderModule`, which `RsvpService` uses to block popular plans during a cooldown. Lore accepts only `ready` (moderated) media; `lore.added` makes the worker redraw the 2×2 collage cover and, for an album's first photo, post squad activity (DECISIONS D-076…D-084).

### Engagement (Phase 8)

`availability`, `crews`, `proposals`, `gamification` and `referrals` sit on top of events and never write its tables: crew sessions and locked votes are created through `EventsService.create` and members invited with `EventInvitesService.grantInvites`; the plan page learns its crew through `EventHooks.crew`; crew chats use a `ConversationGate`. Gamification keeps a facts ledger fed by domain events (`rsvp.checked_in`, `event.completed`, `lore.added`, `reconnect.mutual`, `referral.rewarded`) and evaluates badges, streaks and challenges from it; recaps are written monthly by the worker. Referral credits plug into checkout through `PaymentCredits`, priority passes through `RsvpService.jumpWaitlist`; credit-paid seats are paid out to hosts with a platform-funded direct transfer (DECISIONS D-085…D-095).

### Safety (Phase 9)

`verification`, `safety` and `moderation-tools` own their tables (`verifications`; `trusted_contacts`, `live_location_shares`, `live_location_points`; `user_sanctions`). Content modules stay in charge of their own content: each registers a `ModerationTargetRegistry` handler so reviewers can preview, release or take down messages, plans, Lore, crews, votes, bios and images without reaching into their tables, and each calls `ModerationService.screen` / `flagText` when saving text and `SanctionsReader.assertCanPost` before posting. Held content is a nullable `held_at` (or `bio_held_at` / `caption_held_at`) on the owning row; reads hide it from everyone but its author (or hosts/members). The public live viewer is a Next.js page that reads `GET /v1/live/:token` server-side and polls through its own no-store route; the token is an HMAC, not a stored secret (D-100). Worker jobs: `safety.end-expired-shares` (minutely), `safety.purge-locations` (hourly, D-102), `sanctions.lift-expired` (every 5 minutes).

### Notifications, reminders, calendar and analytics (Phase 10)

Every user-facing nudge goes through `NotificationsService.notify(userIds, kind, params)`. Each kind has a template in `packages/shared/src/notifications.ts` (category, i18n keys, deep-link path, inbox/batch/urgent flags). The inbox stores the kind and params, not text, and renders them at read time in the reader's language (D-106). Push goes out at once, or is held in `pending_pushes` until quiet hours end or the batching window closes; the minutely `notifications.flush-pending` job claims due rows with `FOR UPDATE SKIP LOCKED`, collapses them by key and sends a digest when several are waiting (D-107). The `reminders` module turns domain events (squad requests, invites, edits, cancellations, waitlist offers, completions) and scheduled scans (`reminders.plans`, `reminders.mystery-reveals`) into notifications, claiming each person/plan/kind once in `reminder_log` (D-109). `calendar` serves a per-plan `.ics` and a private iCal feed whose token is an HMAC over user id and version, so a reset revokes old links without storing secrets (D-112). `analytics` maps domain events to analytics events in the worker (one subscription per tracked type) and accepts an allow-listed set of client events, rejecting anything that looks like personal data (D-114).

### Admin dashboard and multi-city (Phase 11)

The admin dashboard is the web app's `/admin` area over `/v1/admin/*`. Who may open each section is one shared matrix (`ADMIN_SECTIONS`, `packages/shared`) read by the API's `@Roles` and the web navigation. City curators are limited to their cities by `AdminScopeService` (common/auth), which every curator-reachable service consults (D-118). Every admin write is audit-logged: services record specific entries in their transaction, and `AuditTrailInterceptor` fills in a generic entry for any admin write that didn't (D-119). Cities are data (`cities`, `neighbourhoods`, `city_waitlist`), and the cities module is a leaf that others import (D-128). Opening a city emits `city.launched`, which the worker turns into notifications. Staff edit, cancel and feature plans through `EventsService.staffUpdate`/`staffCancel` and `AdminEventsService`; discovery reads featured plans and admin-tuned weights (`RankingWeightsService`). Notification wording overrides are applied by `NotificationsService` at render time. The analytics overview reads `analytics_daily`/`analytics_active`, which the worker maintains from domain events (D-125). Ranking weights and template overrides use the same generation-keyed cache as feature flags.

### Realtime

Namespaces `/chat` and `/events`. JWT checked in namespace middleware on connect (`auth.token`). Rooms are joined only after a server-side membership check. Event payloads are typed in `packages/shared/src/socket.ts`. Every realtime action has a REST fallback; messages persist in Postgres. Each socket joins its `user:{id}` room on connect and the API publishes through `@socket.io/redis-emitter` (`RealtimePublisher`) to recipients' user rooms (DECISIONS D-055); `chat:join` records presence only. `/events` carries host-pushed icebreakers to people at a plan. The realtime process answers 404 to every HTTP path but health (D-063).

## 10. Deployment

### Live: Railway + Supabase

Chosen for the lean launch (D-165): a few dollars a month instead of a full AWS setup. Setup steps are in `infra/railway/README.md`; `docs/LAUNCH_CHECKLIST.md` lists what a person must do first.

- **Compute:** Railway project `compassionate-solace`, region Southeast Asia (Singapore), close to the Mumbai database. Railway no longer reads config-as-code, so these settings are entered in each service's Settings; `infra/railway/*.json` is the record of them. Every push to `main` redeploys.
- **Releases:** `api` runs `node dist/infra/database/migrate.cli.js up` as its pre-deploy command, then must pass `/v1/health/live`. A fresh database got reference data and the first super admin from `dist/seed/bootstrap.cli.js` (D-142).

- **Media:** `storage` service running RustFS (`rustfs/rustfs`) with a volume at `/data`, served at `media.touchgrass.co.in`; uploads go there by presigned POST and images are read from `MEDIA_PUBLIC_BASE_URL`.

- **Variables:** project Shared Variables, attached to each service as `${{shared.X}}`; `NODE_ENV=production` set on each service. The web service's `API_URL` is `https://api.touchgrass.co.in`.
- **Sign-in:** Firebase project `touchgrass-e5d1e` (Blaze plan) sends and checks the codes for both the app and the admin console (D-166, D-167).
- **Email:** Brevo's HTTPS API from `hello@touchgrass.co.in` (Railway blocks outbound SMTP below the Pro plan, D-172). Incoming mail to `hello@`, `support@`, `safety@` and `grievance@` is forwarded by Namecheap to the team's Gmail.

### Mobile: EAS

The app is built, signed and updated by Expo's cloud service (expo.dev project `@touchgrass2026s-team/touchgrass`). Profiles `development`, `preview` and `production` in `apps/mobile/eas.json` all point at the live domains (D-168). `eas build` makes the Android/iOS binaries and keeps the signing keys and Firebase config files (`GOOGLE_SERVICES_JSON`, `GOOGLE_SERVICE_INFO_PLIST`); `eas update` sends JavaScript-only fixes to installed apps on each profile's channel (D-170); `eas submit` uploads to the stores (D-141).

### Later: AWS ap-south-1

`infra/terraform` (D-140) describes the scale-up deployment; it is not running. Moving to it changes environment variables, not code. `infra/terraform/README.md` has its first-deployment and release steps.

- **Network:** VPC across 3 AZs with public (ALB, NAT), private (tasks) and data (RDS, Redis) subnets; a NAT gateway per AZ; S3 gateway endpoint; flow logs.
- **Compute:** ECS Fargate services `api` (several processes per task, `API_WORKERS`, D-131), `realtime` (Socket.IO behind a sticky ALB target group, so the polling fallback stays on one task), `worker` and `web`. One API image runs api, realtime, worker, migrations and the bootstrap with different commands. Deployment circuit breaker with rollback; CPU target-tracking autoscaling. An ADOT sidecar sends traces to X-Ray and metrics to CloudWatch.
- **Data:** RDS PostgreSQL 16 + PostGIS, Multi-AZ, forced TLS, Performance Insights, plus a read replica (`DATABASE_REPLICA_URL`); ElastiCache Redis 7 with TLS, auth and `noeviction` (BullMQ needs it).
- **Media:** private S3 bucket behind CloudFront with origin access control; uploads go to S3 by presigned POST.
- **Edge:** ACM certificates, Route 53, ALB routing `api.` to api/realtime and the apex to web; `/admin` can be limited to office IPs; WAF (managed rules, per-IP and OTP rate rules) on the ALB and CloudFront.
- **Secrets:** Secrets Manager under one KMS key: generated app secrets, and a providers secret for third-party keys that Terraform never overwrites. Tasks read both as environment variables; empty values count as unset.
- **Email:** SES domain identity with DKIM and DMARC.
- **Releases:** build and push images tagged with the git SHA → run the migrate task → `terraform apply -var image_tag=<sha>`.
